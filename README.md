## Хэсэг A: Category-Partition

### A1. Сонголт ба төлөөлөх утгууд

| Параметр | Утга | Тайлбар |
|---|---|---|
| from | Valid | данс байгаа, царцаагдаагүй |
| | Frozen | данс байгаа, царцаагдсан |
| | Missing | ийм данс байхгүй |
| to | Valid | данс байгаа, from-оос өөр |
| | Missing | ийм данс байхгүй |
| | SameAsFrom | from-той ижил данс |
| amount | Normal | 0 < дүн ≤ үлдэгдэл, өдрийн лимитэд багтана |
| | Zero | дүн ≤ 0 (0 болон сөрөг утга нэг ангид орно) |
| | OverBalance | хөрвүүлсний дараах дүн > үлдэгдэл |
| | OverLimit | дүн ≤ үлдэгдэл, гэхдээ өдрийн лимитээс хэтэрнэ |
| | ExactBalance | дүн = үлдэгдэл (хязгаарын утга) |
| currency | Same | дансны валюттай ижил |
| | Different | өөр валют, ханшаар хөрвүүлнэ |

**Далд орчны сонголт:** (1) from дансны үлдэгдэл, (2) өдрийн лимитээс үлдсэн хэмжээ, (3) ханш.
Эдгээр нь хүсэлтийн параметр биш ч үр дүнг тодорхойлдог. Жишээ нь `OverBalance` ба `OverLimit`-ийг тусад нь шалгахын тулд лимитийн хоёр өөр төлөв хэрэгтэй:
- **S1:** үлдэгдэл 1000, лимитээс үлдсэн 5000 (лимит том)
- **S2:** үлдэгдэл 1000, лимитээс үлдсэн 500 (лимит жижиг)

### A2. Хязгаарлалтууд

| Утга | Тэмдэглэгээ | Үндэслэл |
|---|---|---|
| from = Frozen | [ERROR] | ERROR_FROZEN буцаах тул бусад утгатай хослуулбал өөр алдааг нууцлана |
| from = Missing | [ERROR] | ERROR_NO_FROM буцаах тул бусад алдааг нууцлана |
| to = Missing | [ERROR] | ERROR_NO_TO буцаана |
| to = SameAsFrom | [ERROR], [IF from ≠ Missing] | ERROR_SAME_ACCOUNT буцаана; from байхгүй бол "from-той ижил" гэдэг утгагүй |
| amount = Zero | [ERROR] | ERROR_BAD_AMOUNT буцаана |
| amount = OverBalance | [ERROR] | ERROR_INSUFFICIENT буцаана |
| amount = OverLimit | [ERROR] | ERROR_LIMIT буцаана |
| amount = ExactBalance | [SINGLE] | хязгаарын утга, үр дүн нь OK; бусад параметрээс хамаарахгүй тул нэг удаа шалгахад хангалттай |
| currency = Different | [property: хөрвүүлэлттэй] | үлдэгдэл ба лимитийг хөрвүүлсний дараах дүнгээр шалгадаг |

**Давуу эрэмбэ:** from байхгүй → from царцаагдсан → to байхгүй → to = from → amount ≤ 0 → үлдэгдэл хүрэлцэхгүй → лимит хэтэрсэн.
Үндэслэл: эхлээд оролцогч дансуудын байдлыг (хямд, бүтцийн шалгалт), дараа нь дүнгийн хүчинтэй байдлыг, эцэст нь үлдэгдэл шаардсан бизнесийн шалгалтыг хийнэ. Энэ нь спецификацид дүрмүүд бичигдсэн дараалалтай нэг чиглэлтэй.

**"N → M" тооцоо:**
- Бүрэн олонлог: `3 × 3 × 5 × 2 = 90`
- [IF] хязгаарлалтаар утгагүй хослол хасна (from = Missing ∧ to = SameAsFrom: `1 × 1 × 5 × 2 = 10`): `90 → 80`
- [ERROR] утга бүрийг нэг удаа (7: Frozen, Missing, to-Missing, SameAsFrom, Zero, OverBalance, OverLimit), [SINGLE]-ийг нэг удаа (1), үлдсэн хэвийн утгуудаас (from = Valid, to = Valid, amount = Normal, currency = Same/Different) 2 хослол:
  `7 + 1 + 2 = 10` → **90 → 10**

(PICT-ийн моделд SINGLE утга ордоггүй тул тэнд бүрэн олонлог `3 × 3 × 4 × 2 = 72`. transfer.model-ийн 3 `IF` хязгаарлалтын дараа хүчинтэй хослол `72 → 40`.)

## Хэсэг B: PICT

### B1. Браузерын жишээ (`browser.model`)

| Түвшин | Мөрийн тоо | Файл |
|---|---|---|
| Бүрэн олонлог (3 × 3 × 2 × 2 × 2 × 2) | 144 | - |
| 2-way (pairwise) | **10** | `results/browser-2way.txt` |
| 3-way (`/o:3`) | **20** | `results/browser-3way.txt` |

**2-way дүн:** Лабын даалгаварт лекц дээр гараар 9 мөрөнд багтаасан бол PICT 10 мөр гаргасан, өөрөөр хэлбэл 1 мөр илүү.
PICT нь greedy алгоритм ашигладаг: алхам бүрт одоогоор хамраагүй хамгийн олон хосыг шинээр хамарсан мөрийг сонгоно. Энэ арга хурдан боловч глобал хамгийн цөөн мөртэй covering array олохыг баталгаалдаггүй. Гараар бол хэв шинжийг харж, хамгийн цөөн мөрийг олж болдог.

**3-way дүн:** Бүрэн олонлог 144 мөрөөс 3-way хамралтыг 20 мөрөөр (ойролцоогоор 14%) хангасан. Хамралтын түвшинг 2-оос 3 болгоход мөрийн тоо 10-аас 20 болж 2 дахин өссөн ч бүрэн олонлогоос хамаагүй бага хэвээр байна.

README-д бичсэн мөрийн тоо нь `tail -n +2 results/browser-2way.txt | wc -l` болон `tail -n +2 results/browser-3way.txt | wc -l` командын үр дүнтэй таарна (толгойн мөрийг тооцоогүй).

### B2. Шилжүүлгийн модель

Model файлууд: `transfer-nc.model` (хязгаарлалтгүй), `transfer.model` (A2-ын 3 IF хязгаарлалттай), `transfer-neg.model` (алдааны утгыг `~`-ээр тэмдэглэсэн).

| Хувилбар | Файл | Мөрийн тоо | Happy path мөр | Нэг мөрийн алдааны тоо |
|---|---|---|---|---|
| Хязгаарлалтгүй | `results/transfer-nc.txt` | **13** | 1 | 0-3 (11 мөрөнд 2+ алдаа) |
| Хязгаарлалттай | `results/transfer.txt` | **13** | 1 | 0-3 (8 мөрөнд 2+ алдаа) |
| Сөрөг утгатай (`~`) | `results/transfer-neg.txt` | **16** | 2 | 0-1 (2+ алдаатай мөр байхгүй) |

(Бүрэн олонлог `3 × 3 × 4 × 2 = 72`, A2-ын 3 хязгаарлалтын дараа хүчинтэй хослол 40.)

**Гаралтын ажиглалт:**
- `transfer-nc`-д `Missing, SameAsFrom, Zero` гэх мэт утгагүй хослол гарсан (from байхгүй бол to нь from-той ижил байх боломжгүй). Мөн `Missing, Missing, OverBalance` мөр нь 3 алдааг зэрэг агуулах тул ямар алдаа буцахыг тодорхойгүй болгож байна (error masking).
- `transfer`-д хязгаарлалтын ачаар утгагүй хослол алга болсон ч мөрийн тоо 13 хэвээр, 2+ алдаатай 8 мөр үлдсэн (жишээ нь `Frozen, SameAsFrom, Zero` нь 3 алдаатай). Эдгээр мөрийн oracle нь давуу эрэмбээс хамаарна, тиймээс "ямар алдааг шалгаж байна" нь тодорхой биш.
- `transfer-neg`-д нэг мөрт ихдээ 1 алдаа орсон тул мөр бүр яг нэг алдааг шалгана. Мөрийн тоо 16 болж нэмэгдсэн нь алдаа бүрийг тусад нь шалгаж байгаагийн үр дүн.

**`~` хэрэглэхэд A2-ын хязгаарлалт хэрэгтэй хэвээр үү?** Үгүй. `~` утга нэг мөрт ганц л орох тул `Missing + SameAsFrom` гэх мэт утгагүй хослол гарахгүй. Иймд A2-ын [ERROR] тэмдэглэгээг `~` бүрэн орлож, `transfer-neg.model`-д IF хязгаарлалт бичих шаардлагагүй болсон. Харин A2-ын [SINGLE] утга (`ExactBalance`) PICT-д огт ороогүй тул гараар тусад нь тестлэнэ.

### Бодит тест кейсүүд
Setup: данс A (үлдэгдэл 1000 USD, өдрийн лимитээс 5000 үлдсэн), данс B байгаа, ханш 1 EUR = 1.1 USD.

| # | Эх мөр | Setup | Оролт (body) | Oracle |
|---|---|---|---|---|
| 1 | `transfer-neg`: Valid, Valid, Normal, Same (happy path) | A: 1000 USD | `{"from":"A","to":"B","amount":100,"currency":"USD"}` | 201 `{"result":"OK"}` |
| 2 | `transfer-neg`: Valid, Valid, ~OverBalance, Different (1 алдаа) | A: 1000 USD | `{"from":"A","to":"B","amount":1500,"currency":"EUR"}` | 200 `{"result":"ERROR_INSUFFICIENT"}` |
| 3 | `transfer`: Frozen, SameAsFrom, Zero, Different (3 алдаа) | A царцаагдсан | `{"from":"A","to":"A","amount":0,"currency":"EUR"}` | 200 `{"result":"ERROR_FROZEN"}` (давуу эрэмбээс: from-ийн шалгалт эхэлнэ) |


### B3. Гар A3 хүснэгт ба PICT-ийн харьцуулалт

**Алдааны семантик.** Гар A3 хүснэгт нь алдааны семантикийг илүү сайн барьсан. Мөр бүрт хүлээгдэх үр дүн (`ERROR_FROZEN`, `ERROR_LIMIT` гэх мэт) тодорхой бичигдсэн, давхар нөхцөлийн мөр (11-13) давуу эрэмбээс гарсан oracle-той. PICT-ийн гаралтад зөвхөн утгын хослол байх бөгөөд хүлээгдэх үр дүнг тэр өөрөө тодорхойлдоггүй. Жишээ нь `transfer.txt`-ийн `Frozen, SameAsFrom, Zero` мөрийн oracle-ийг би давуу эрэмбээсээ гараар гаргасан. Мөн PICT нь далд орчны сонголтыг (үлдэгдэл, лимитийн төлөв S1/S2) мэддэггүй, ингэснээр `OverBalance` ба `OverLimit`-ийг ялгах setup-ыг би тест кейсэд гараар нэмсэн. SINGLE утга `ExactBalance` PICT-ийн моделд ороогүй.

**Хосын хамралт.** Харин хосын хамралтыг PICT баталгаажуулдаг. Гар A3-д ийм баталгаа байхгүй. Жишээ нь A3-т `Frozen` утга зөвхөн `Same` валюттай (мөр 3, 11) орсон тул `Frozen + Different` хос хамрагдаагүй, мөн `Frozen + OverBalance` хос ч алга. Харин `transfer-nc.txt`-ийн 13 мөр нь бүх параметрийн хос бүрийг дор хаяж нэг удаа хамарсан. Ингэхдээ PICT нь 72 хослолын оронд 13 мөр өгсөн.

**`~` хувилбар.** `transfer-neg` нь хоёр аргын давуу талыг холбосон: PICT-ийн автомат хамралтыг хадгалсан хэвээр мөр бүрт яг нэг алдаа оруулдаг тул category-partition-ий [ERROR] семантиктай дүйнэ. Үүний ачаар oracle нь давуу эрэмбээс хамаарахгүй, мөр бүр шууд нэг алдаатай харгалзана.

## Дүгнэлт

1. Энэ лабд би шилжүүлгийн функцийн тестийг category-partition аргаар гараар, мөн PICT-ээр хоёр янзаар зохиосон.
2. Гараар зохиохдоо 90 хослолыг [ERROR], [SINGLE], [IF]-ээр 10 болгон бууруулсан (90 → 10), харин PICT 72 хослолоос 13 мөр гаргасан.
3. Гар арга нь алдааны семантик, давуу эрэмбэ, далд орчныг (лимит, үлдэгдэл) ойлгож oracle-оо тодорхойлоход илүү сайн ч, бүх хос хамрагдсан эсэхийг баталгаажуулж чаддаггүй.
4. PICT нь хосын хамралтыг баталгаажуулдаг ч greedy алгоритмтай тул хамгийн цөөн мөрийг олохыг баталдаггүй, браузерын жишээнд лекцэд дурдсан 9 мөрөөс нэг илүү буюу 10 мөр гаргасан.
5. Алдааны утгыг энгийн утга шиг бичихэд PICT нэг мөрөнд хэд хэдэн алдаа хослуулж (`Frozen, SameAsFrom, Zero`) error masking үүсгэсэн.
6. `~` тэмдэглэгээ энэ асуудлыг шийдэж, мөр бүрт яг нэг алдаа оруулсан бөгөөд A2-ын IF хязгаарлалт хэрэггүй болгосон.
7. Хамгийн их бодол шаардсан алхам нь A2-ын "N → M" тооцоо байсан: [ERROR] утга бүрийг ганцаарчлан, [SINGLE]-ийг нэг удаа тестлэхээр тооцоод 90 хослолыг 10 болгохдоо аль утга алдаа, аль нь хязгаарын утга гэдгийг зөв ангилах хэрэгтэй байсан бөгөөд PICT-ийн моделд SINGLE утга ордоггүй тул 90 биш 72 хослолоос эхэлдгийг ялгаж ойлгох шаардлагатай болсон.
8. Шинэ зүйл нь PICT-ийг эх кодоос нь cmake-ээр бүтээж суулгах байсан: Windows дээр ажиллахгүй тул WSL2 (Ubuntu) суулгаж, түүн дотор `apt`, `cmake`, `g++`-ээр бүтээн `results/pict-build.txt`-д commit хэш болон хэрэглээний зааврыг баталгаа болгон хадгалсан.
9. Практикт хамгийн сайн нь хоёр аргыг хослуулах: гараар утга, алдааны ангилал, oracle-ыг тодорхойлж, PICT-ээр хослолыг автоматаар үүсгэх.
